# 渠道发行工作表维度体系

> **场景模板**：这里提供可迁移的游戏渠道发行维度骨架；游戏、区服、渠道、节点和口径值均应从 `config/example.yaml` 复制并配置，不代表任何具体游戏或发行项目。

```mermaid
flowchart LR
    A[复制配置模板] --> B[填写游戏与渠道占位项]
    B --> C[核对标签和统计口径]
    C --> D[按 A/B/C/D 判定信息性质]
    D --> E[执行证据与敏感信息闸门]
    E --> F[输出可追溯的表格结果]
```

这套模板把游戏渠道发行中的表格、标签和治理规则整理成可迁移的业务骨架。换项目时替换配置，不需要重写维度定义和工作流。

它不是项目资料库，不含成员、账号、表地址、真实游戏名、时间窗或统计数字。示例值均为占位符。

第一次使用先读 `分发说明.md`；需要快速配置时看 `使用说明_一页纸.md`。完整说明依次涵盖三层架构、维度体系、工作流、AI 边界和迁移方法。

> **包版本**：1.1.0｜生成日期：2026-11-12｜分发状态：**可作为分发版使用**；通用骨架已定，使用方需自行确认的项目见 §8 与 `分发说明.md`

## §0 工作逻辑

一条表格记录依次完成四件事：确定游戏、渠道、节点和时间；判断信息类别；判断 AI 能否处理；最后检查口径、证据和使用权限。它们对应定位、分类、性质和治理四个维度族。

```
        定位族                分类族              性质族              治理族
   ┌──────────────┐    ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
   │ 挂到哪：      │    │ 是什么：      │   │ 能不能自动：  │   │ 算不算对：    │
   │ 游戏/区服/    │───▶│ 信息域/类别/  │──▶│ A事实 B状态   │──▶│ 口径/归一化/  │
   │ 渠道/节点/    │    │ 表种/模板/    │   │ C判断 D敏感   │   │ 敏感/证据/    │
   │ 时间/阶段     │    │ 聚居度/层次   │   │ → 决定动作    │   │ 授权/验收     │
   └──────────────┘    └──────────────┘   └──────────────┘   └──────────────┘
        坐标                 归类                 决策                 闸门
```

## §1 三层架构：为什么它能「换项目自适应」

| 层 | 装什么 | 本包里的文件 | 换项目时 |
|---|---|---|---|
| **① 通用骨架层** | 维度定义、维度关系、工作流、AI 边界、标签命名与字段规则、快速上手、分发元信息 | `README.md`、`WORKFLOW.md`、`tags/tag_schema.yaml`、`SKILL.md`、`使用说明_一页纸.md`、`分发说明.md`、`CHANGELOG.md` | **不动**（这是可迁移的部分） |
| **② 可换配置层** | 游戏清单、区服、渠道口径与别名、节点词表、时间窗、角色名、阶段包、表地址 | `config/example.yaml`（新项目复制改名） | **整层替换**，骨架不改 |
| **③ 标签数据层** | 按配置层生成的具体标签实例、动作映射、状态 | `tags/tags.yaml` | **随配置刷新** |

**自适应 = 换配置，不是零配置自动适配。** 换项目能自动带走的是骨架、规则、标签定义和工作流；带不走的是资料、渠道名单、时间窗、成员、口径数字——这些必须由新项目重新喂一遍配置层。做不到零配置就能跑，如实说在前面。

## §2 维度体系（核心）

> 项目历史里散落着「12 信息域 / 5 定位维度 / 四坐标 / 表种七分 / 信息性质四分 / 15 类信息类别 / 聚居度三分 / 16 类模板 / 阶段包 / 口径 K1–K5」等多套说法。
> 本体系把它们**整合成四个维度族**，每族职责单一、互不重叠。下面是完整定义。

### 2.1 定位族 —— 一条记录挂在哪（坐标维度）

| 维度 | 定义 | 划分依据 | 适用范围 | 关键字段 / 取值 | 业务用途 |
|---|---|---|---|---|---|
| **游戏** | 项目主体 | 立项单位，一号区分 | 全部记录 | `game_id`、标准名、别名 | 决定找哪套资料；跨游戏不可互证 |
| **区服** | 游戏的下一级运营单元 | 同一游戏不同发行区域/版本 | 有分区服的项目 | `server`（如国服/国际服） | 跨区服不可互证；区服是游戏的下一级 |
| **渠道 / 模块** | 分发或曝光的落点 | 按平台归属分层；模块是渠道的**聚合层** | 渠道级内容 | `channel`、`module`（聚合口径）、内/外渠分类 | 决定找哪张渠道表；**「全平台/全渠道」不能当某渠道答案** |
| **节点** | 业务时间锚点 | 版本/活动/渠道节点 | 有节奏的业务 | `node`（节点名 + 日期）、活动类型 | 同名不同节点不算覆盖；节点须与渠道同时确认 |
| **时间** | 具体时间点或区间 | 日期轴 / 周次 / 检查时点 | 全部记录 | `date`、`week`、`check_point`、时间窗 | 对齐日历、判定证据是否在窗口内 |
| **阶段** | 生命周期粗分区 | 预约期 / 首发期 / 运营期 | 项目全程 | `phase`（可叠加：主阶段+局部阶段） | 决定启用哪套模板、指标与校验重点 |

**三者关系澄清（历史里最容易打架的一处）**：
「5 定位维度（游戏×区服×渠道×节点×日期）」「四坐标（游戏×模块×渠道×时间）」「阶段包」不是三套体系，是**同一套坐标的不同切面**——模块是渠道的聚合层，阶段是时间的粗分区。配置层只维护一份坐标字典，避免各写一套。

**渠道口径（配置层示例，脱敏占位）**：内渠 / 外渠 / 平台（货架）/ 官方直营 / 独立统计。**铁律：跨口径不可互证**；查某游戏的渠道前必须先确认用哪一套口径。渠道名比对前必做归一化（剥分类前缀、查别名表）。

### 2.2 分类族 —— 这条记录是什么（归类维度）

| 维度 | 定义 | 划分依据 | 适用范围 | 关键字段 / 取值 | 业务用途 |
|---|---|---|---|---|---|
| **信息域** | 业务领域的大类 | 按业务职能划分，12 类 | 全项目资料组织 | 项目基础／节点／排期／任务与进度／渠道合作／资源位／投放／素材／效果数据／奖励与 CDK／预算与目标／文档与人员 | 建资料地图时的一级分类 |
| **信息类别** | 记录在业务链条上的位置 | 按「它在链条上的位置」而非文件划分，15 类 | 检索与取法 | 负责人／上线时间／平台要求／文案／需求／规则／区服／资源排期／链接／游戏／活动内容／素材／推广活动／版本活动／运营活动 | **决定用哪套取法**（见聚居度） |
| **聚居度** | 一类信息散在几份表里 | 分散表数：≤10 聚居／11–50 半聚居／>50 弥散 | 所有检索任务 | `density`: clustered / semi / scattered | **聚居→整表映射；半聚居→定位区域；弥散→只能靠坐标**。只有「运营活动」类天然聚居 |
| **表种** | 表的用途类型 | 按「管什么」划分，7 种 | 表结构识别 | 周会表／渠道工作总表／资源素材需求表／节点筹备 Checklist／数据表／活动礼包表／专项表 | 决定填写说明书、行维度、主要信息性质 |
| **模板类型** | 可复用的表结构 | 规划/执行/复盘/管理四组，16 类 | 生成新表时 | 版本发布日历、资源排期日历、进度 Checklist、渠道合作总览、CDK 台账… | 骨架复用；**结构与实例分离** |
| **层次** | 记录所在的表层 | 索引层 vs 明细层 | 跨表汇总 | `layer`: index / detail | 索引层（周会表）里的素材/文案/资源位是「句子里的词」不是字段；明细在专题表。**两层缺任务编号时靠人连** |

**归类维度的关键结论**：材料在表里「聚居还是弥散」直接决定取法，不能统一用关键词检索。这是「先建地图、按需取用」的底层原因。

### 2.3 性质族 —— AI 能不能自动处理（决策维度，全体系的中枢）

| 类 | 定义 | 判据（一句话） | 自动填？ | 人工补时 AI 做什么 |
|---|---|---|---|---|
| **A 可查事实** | 已写在资料里的客观内容 | 「上周/去年的资料里会不会写？」会 → A | **能**，必须附坐标 | 给候选 + 精确出处 |
| **B 实时状态** | 此刻由人维护的进展 | 「只有今天才知道」→ B | **不能，不猜** | 给格子坐标 + 上期计划当核对项，出待确认清单 |
| **C 判断决策** | 需要人拍板的取舍 | 优先级、预算取舍、是否补资料 | **不能** | 只出选项 + 依据，等人拍板 |
| **D 敏感** | 涉及人/钱/权限 | 负责人、账号、CDK、预算 | **不读**（按字段语义扣留） | 指路，不代填 |

**A/B/C/D 是「填表可行性」的唯一判据**：所有填表、找资料、生成表任务，先给每格打上性质标签，再决定动作。判定口诀见 `SKILL.md`。

### 2.4 治理族 —— 算不算对 / 能不能用（闸门维度）

| 维度 | 定义 | 关键规则 | 适用范围 | 业务用途 |
|---|---|---|---|---|
| **判定口径** | 「什么算找到」的规矩 | ① 时间窗内才认（固定维度豁免）② 同名不同节点不算 ③ 扣留格单列且必须出清单 ④ 碰巧写对不计分 ⑤ 不同事项禁止混谈互推、跨赛季/跨区服不可互证、资料自标"施工中"不可作证 | 找内容/填写/验收 | 不改业务事实，只决定算不算对 |
| **数字口径** | 计数与分母 | **任何比例必须标分母**；有效分母 = 全量 − 扣留；口径数字分「有效/待定/废弃」三态 | 所有统计与汇报 | 防止数字口径打架 |
| **名称归一化** | 比对前的统一 | 大小写不敏感、剥分类前缀、查别名表、全角半角与空白统一；**规则取自资料内部写法，禁止从答案反推** | 所有比对与写入 | 解决「找到了却对不上」 |
| **敏感策略** | 按字段语义扣留 | 白名单优先于形态规则；动作分 `withhold`/`header_only`/`count_only`/`mask`；**禁止按列坐标配规则** | 所有读取 | 防两头：漏扣与过度扣留都是风险 |
| **授权边界** | 能不能写、写到哪 | 原表只读；写入只能在授权新表/独立副本且先差异预览；群聊仅只读取证 | 所有写入 | 防止越权与数据外发 |
| **证据规则** | 每步留痕 | 每结论带坐标（来源/记录/列/原文）；查不到也留「查过什么」；三通道取证（群聊/文档/本周新建文件） | 全流程 | 可回溯、可复核 |
| **验收裁判** | 交付前把关 | 逐格必答、召回闸门、冻结答案+代码判题（不用模型阅卷）；**提覆盖率前必须先有裁判** | 交付与考试 | 覆盖率是安全阀，不是越高越好 |

### 2.5 维度间关系（六条，业务链条）

1. **游戏 → 区服**：区服是游戏的下一级；跨区服资料不可互证。
2. **区服 → 节点活动**：活动分版本活动 / 推广活动 / 运营活动三类，**写法完全不同，不能混谈**。
3. **活动 → 需求**：一个活动产生多条需求（素材、礼包、资源位）；需求最集中在项目总表类资料。
4. **需求 → 交付物**：需求落地成文案、素材、链接。
5. **交付物 → 上线**：受**平台要求与规则**约束（规格、审核、尺寸）——这一类通常最稀缺，是缺口而非没检索到。
6. **负责人贯穿全链**：不单独属于某一类，是挂在每一行上的外键；属于 **D 敏感**，只作归属不代填。

**四族如何串起来**：定位族给坐标 → 分类族定取法 → 性质族决定「AI 能不能动这格」→ 治理族决定「动了算不算对」。任一族缺位，汇总必错。

## §3 完整业务工作流程

分层工作流的**逻辑链条、每层工作方式、参与角色、输入输出、关键节点、按业务目标选层的规则**，全部写在 `WORKFLOW.md`。这里只给主干：

```
L0 定范围建地图 → L1 认表种读填法 → L2 找内容(四路召回·逐格必答) → L3 按 A/B/C/D 定性
   → L4 按目标选产物(骨架自动+进展出清单) → L5 验收(坐标/闸门/回归)
```

- **工作方式**：查表+映射，不生成事实；先建地图不通读；逐格必答；每步留痕；差异预览后再写。
- **参与角色（脱敏）**：业务方（拍板/补资料）、渠道负责人、PM/执行支持、内容评审（独立持答案）、规则质检、AI 助手、确定性脚本。
- **关键节点**：资料范围确认、性质判定、缺口/冲突集中确认、写入差异预览、验收闸门。
- **按目标选层**：不是每条线都跑满——例如「每周复制周会骨架」这类活不需要召回率指标，只跑 L0/L1/L3/L4。

## §4 AI 可赋能的业务环节（目标 / 所需信息 / 预期产出 / 应用边界）

| # | 环节 | 目标 | 所需信息 | 预期产出 | 应用边界 |
|---|---|---|---|---|---|
| 1 | **结构识别** | 看懂每格要什么 | 表头、前 5 行、日期轴、填写说明书 | 表种判定、行列/分组含义、字段语义 | 只识别语义，不猜业务值；陌生版式先问 |
| 2 | **建资料地图** | 先知道「有什么」 | 文件清单、来源身份、更新时间 | L1 目录卡 / L2 结构指纹 / L3 坐标索引 | **不通读**；有地图不等于已细审 |
| 3 | **检索与引用**（A 类） | 找全可查事实 | 允许的来源清单、节点/渠道/日期词、别名表 | 候选内容 + 精确坐标 + 原文片段 | **必须附坐标**；四路召回取并集；禁止通读整包 |
| 4 | **名称归一化** | 解决「找到却对不上」 | 资料内部写法、别名表、前缀规则 | 标准化名称、等价匹配 | 规则禁止从答案反推 |
| 5 | **性质判定** | 决定这格能不能自动 | 字段语义、敏感白名单、上期计划 | 每格 A/B/C/D 标签 + 动作 | 判错会直接导致编造或越权，属高危环节 |
| 6 | **骨架生成/复制** | 稳定结构全自动 | 上期骨架、固定维度清单 | 新表骨架（100% 可复制） | 只复制结构，**不复制进展** |
| 7 | **缺口/冲突清单**（B/C 类） | 人工补时立刻知道往哪填 | 空格坐标、上期计划、三通道证据 | 待确认清单 + 单元格坐标 + 历史同节点建议 | **不猜、不硬填**；空白不得默认已完成/未完成 |
| 8 | **消歧与把握度** | 处理同名/跨赛季/冲突 | 节点、时间窗、来源坐标 | 高/中/低把握 + 理由；冲突标红上报 | **助手不选边**；相似度不等于事实可信度 |
| 9 | **格式校验/回归** | 不破坏原格式 | 冻结答案、格式基线 | 代码判题结果、退化可撤回 | 不用模型阅卷；不把格式回归当业务内容考试 |
| 10 | **差异预览** | 写入前防误改 | 目标表、旧值、来源、确认人 | 逐格差异（同值跳过/冲突问） | **原表仍不写**；只在授权新表/副本 |

**AI 只干 4 件机器干不了的活**：读懂结构、写检索式、消歧、给把握度+理由。检索/匹配/打分/对账全部走确定性脚本。

**四条硬边界**：① 不生成业务事实 ② 不猜实时状态（B）③ 不替人拍板（C）④ 不读敏感（D）。此外：不写原表、不发消息、不拉群、不跨赛季互证、资料打架不选边。

## §5 业务体系标签库

标签库是**给 AI 判定用**的机器可读结构，完整定义拆在两个文件：

| 文件 | 内容 |
|---|---|
| `tags/tag_schema.yaml` | 标签**分类、层级、命名规则、字段定义、适用场景、关联维度、维护扩展规则、状态机、版本演进** |
| `tags/tags.yaml` | 脱敏后的**标签实例**（四族 × 动作 × 状态），含 `action` 字段直接告诉 AI「能不能填 / 去哪找 / 要不要扣留」 |

设计要点（借鉴业界受控词表，见 §7）：
- **命名**：小写英文 + 点分层级 + 动词/名词收尾；版本、数值、项目代号**不进名字**。
- **稳定 ID**：标签有不变 ID，改名不改 ID；别名单独登记。
- **只增不改**：语义变了**新增 + 废弃旧标签 + 迁移窗口**，绝不原地改名或删除。
- **退役不删除**：标 `deprecated` + `superseded_by`，历史引用不断链。
- **一个维度只一个值**：需要两个值就拆成两条记录或新开维度，不造复合标签。
- **未知标签拒绝**：不在词表里的标签写入即拒，落「未识别清单」上报，不许 AI 自造。

## §6 换项目怎么改（迁移 / 自适应 SOP）

1. **整包拷走**：把本目录拷到新项目的 `{{SKILL_ROOT}}/` 下或任意资料目录。骨架层文件不动。
2. **复制配置**：`config/example.yaml` → 改名成新项目的配置；逐项填真实值（清单见该文件注释）。
3. **必改项**：游戏清单、区服、渠道口径与别名、节点词表与日期、时间窗、阶段包、角色名、资料地址、口径数字与分母。
4. **刷新标签（通常＝确认无需改）**：本包 59 个标签**全为 `generic`**，无项目专属实例，换项目默认不用动 `tags/tags.yaml`；`tag_schema.yaml` 永远不动。只有三种情况才刷新：补 `aliases`、新增 `project_specific` 标签、标 `deprecated`（详见 `使用说明_一页纸.md` 的「刷新标签真相」）。
5. **重标性质**：新项目资料进来后，逐格重新打 A/B/C/D 标签——性质是资料属性，不能继承。
6. **自检 + 记版本**：跑 §9 六项分发版自检；在 `CHANGELOG.md` 记一笔包版本（§10 只记体系正文的变更）。

**明确带不走的**：具体资料、渠道名单、时间窗、成员与账号、表地址、统计数字、已确认的节点事实。这些不是「不可迁移」，而是**属于配置层、必须重新喂**。

**支持后续迭代**：分层文件互不耦合（改配置不动骨架、加标签不动工作流）；所有改动走「只增不改 + 升版本 + 回归」；每次变更留痕。

## §7 开源调研与方法论借鉴（2026-11-12）

调研了公开的四类相近方向，**结论：垂直的“游戏渠道发行维度体系”没有可直接复用的现成方案（同类项目多是通用游戏数据看板、遥测埋点或运营决策平台，与“表格填法/维度治理”不是一回事），能借的是通用元数据与受控词表方法。**

| 借鉴来源（公开 README/文档） | 借了什么规矩 | 落在本包哪里 |
|---|---|---|
| 游戏遥测与事件字典规范 | 命名小写+下划线+动词收尾、版本/数值不进名字；**语义只增不改**；字典是唯一事实来源、一张表定全；新增前先答“回答什么问题/谁用/半年后还有没有人看”；属性最小化 | `tag_schema.yaml` 命名与扩展规则 |
| 公共术语表与分类方法 | 稳定 ID、首选名/别名/隐藏名、层级(broader)与关联(related)、**退役只标 deprecated 永不删除**、生命周期状态 | `tag_schema.yaml` 层级与状态机 |
| 版本化受控词表实践 | 封闭版本化词表、未知标签写入即拒、**一个维度只一个值**、必填维度表、改动走评审+升版本、改名=新增+废弃 | `tag_schema.yaml` 维护扩展规则 |
| 分层数据建模与层间质量闸门 | 原始层→标准层→应用层分层、参数化换源即复用、**层间闸门**、配置驱动而非硬编码 | §1 三层架构、`WORKFLOW.md` 分层 |
| 术语退役/文档生命周期 playbook | 新增与废弃的先后顺序、**改名=新增+废弃+迁移窗口**、`last_verified`（人确认）与「最后编辑」分开 | §6、`tag_schema.yaml` |

**三方案对比与推荐**：
- *直接使用现成项目* → 不推荐：都是重型数据平台/分析看板，场景不匹配，且要引入数据库、服务与依赖。
- *基于现成项目二次开发* → 不推荐：改造成本高于收益，本包要的是「规矩与映射」，不是软件。
- *自主整理封装（本包）* → **推荐**：把已敲定的业务结论抽成「骨架 + 配置 + 标签」三层，零依赖、零部署、整包可拷。

**风险如实说明**：本包**只借鉴方法论，未下载、未复制、未引入任何开源代码或运行时依赖**，因此许可证合规、部署难度、依赖风险均**不适用**（无引入即无风险）；调研依据为检索到的公开 README/文档描述，未对上游项目逐一做许可证与维护状态审计——若将来真要引入某个项目，须另行核查许可证、维护活跃度与依赖链。

**对外分发**：使用条款、限制与免责统一写在 `分发说明.md`；本包可作为分发版直接使用。

## §9 分发版自检（6 项）

1. **对齐**：与既有结论逐条比对，无自相矛盾；同一说法在不同文件一致（尤其「刷新标签」「骨架层文件清单」）；未定项已标「未定」，不包装成已定。
2. **脱敏**：全文无真实姓名、账号、表地址、群名、口令、CDK、预算金额、**任何具体项目统计数字**；来源项目实证／历史教训已标注为「背景，不构成通用保证」。
3. **标签**：每个标签字段齐全、命名自洽、无复合值、无重复 ID；**规则与实例一致**（前缀、引用类型、状态枚举、action_mapping）。
4. **覆盖**：README 四块（维度体系 / 工作流 / AI 边界 / 标签库）不缺项，迁移 SOP 可执行。
5. **包完整性**：`分发说明.md` 的文件清单与实际文件一致；包版本在 `SKILL.md` / `README.md` / `CHANGELOG.md` 一致；`CHANGELOG.md` 有对应条目。
6. **无悬空引用**：文档引用的文件都在包内；不出现来源项目内部文件名或身份；zip CRC 通过、包内 3 个 YAML 可解析。
